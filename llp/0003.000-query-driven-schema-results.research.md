# LLP 0003.000: A schema shaped by its queries: results

**Type:** Research
**Status:** Draft
**Systems:** Schema, Reads, Research
**Author:** Adam Zvada / Claude
**Date:** 2026-09-25
**Related:** LLP 0003, LLP 0002, LLP 0001

## Summary

A query log, a model-proposed and code-tested schema migration pass, and compiled question templates were built and
run on the 5,050-message database (round 4). They were then scored on 105 questions the optimizer never saw.
- **Accuracy.** On the evolved schema the hybrid reader went from 61.0% to 70.5%, and the deterministic reader alone
  from 49.5% to 61.9%.
- **Novel question shapes** rose from 24% to 44%.
- **No regression** on round 4's 72 questions (81.3% → 83.3%).
- **Compiled templates** answered 14 recurring questions in ~4 ms (vs ~1 s) with none wrong.
- **Cost.** The optimization itself cost under $0.10 and used no gold answers.
- **Against the pre-registered thresholds** (LLP 0003#hypotheses) the final run is mixed: the hybrid target holds,
  while the deterministic target misses by 1.25 points and template coverage falls short (35% vs 50%). An earlier run
  of the same pipeline passed both.
- **Most instructive finding: the advisor's proposals vary from run to run.** The code-side tests keep every kept
  migration correct, but what gets proposed, and so what improves, varies.

All numbers here are graded by rules against the simulator's truth unless marked otherwise.

## What ran

`deprecated/python/lab/bench/workload.py` runs these steps in order; the files are listed in [Files](#files).
1. **`log`.** The 80 past questions went through the hybrid read path on the round-4 database. The results went to
   `_queries`: plans, verifier scores, and six signals plus `variants` (a filter on one spelling of a value stored in
   several).
2. **`optimize`.** `deprecated/python/lab/systems/schema_advisor.py` ran up to 3 rounds. Each proposal is tested on a scratch copy and
   rejected if:
   - it duplicates a column under the same names
   - it lumps together values an existing category column keeps apart
   - it decides a real value for < 70% of the rows in its scope
   - its rules agree with Jev on < 85% of a sample
   - the questions it claims to serve don't get ≥ 0.05 healthier on replay

   Kept migrations are applied with the specs recorded (`_derived`, `_migrations`). Later rounds see only the flagged
   questions nothing serves yet.
3. **`compile`.** The past questions were re-asked on the new schema. Their trusted plans (77 of 80) were compiled into
   templates, and each template was kept only if it reproduces the logged answer on ≥ 2 questions and on every
   question it matches.
4. **`evaluate`.** The 105 future questions ran on the base and evolved databases with three readers each:
   deterministic, agent, and hybrid at a verifier threshold of 0.7. Compiled templates were tried first on the
   evolved one. The 72 round-4 questions ran as a regression check, Jev-graded.
5. **`latency`** (live, cache off, one question at a time) and **`physical`** (no model).

## Results

**Future questions (105):**

| | deterministic | agent | hybrid | answered without an LLM |
|---|---|---|---|---|
| base schema | 49.5% | 60.0% | 61.0% | 75 |
| evolved schema | **61.9%** | 64.8% | **70.5%** | 77 |
| evolved + compiled templates | | | 70.5% | 77 (14 in ~4 ms) |

**By group, hybrid (deterministic in brackets):**

| group | base | evolved |
|---|---|---|
| same shapes and phrasings as the log, new parameters (40) | 75.0% (67.5%) | **87.5%** (85.0%) |
| same shapes, new phrasings (40) | 70.0% (62.5%) | 70.0% (62.5%) |
| novel shapes (25) | 24.0% (0%) | **44.0%** (24.0%) |
| round 4's 72 questions (Jev-graded) | 81.3% (68.1%) | 83.3% (72.2%) |

**Where the gain comes from** (deterministic, base → evolved):
- average bill per kind: 38% → 88%
- spend on a kind with a person: 0% → 80%
- total spend on a kind: 25% → 50%
- counts of a kind: 38% → 50%

Health controls (sleep, weight, runs) stayed at 100%. Climbing counts stayed at 25%: the planner's `title` filter
drops some sessions, which is a write-side issue.

**Why the new phrasings didn't move.** Mostly table routing for unusual wording, which no schema change can fix:
- "Biggest bill for a lunch in Prague?" was routed to `books`
- "…night of drinks in San Francisco?" was routed to `movies`
- "use Uber or Bolt" was routed to `body_measurements`

The rest are write-side near misses: 288 vs 289 coffees, 172 vs 174 lunches (the late-night date issue, LLP 0002).

## Hypotheses

Two full runs of the same pipeline. Run A came before three fixes that affect both conditions: counts, template
mapping, and a second association pass. Its per-question file was overwritten by run B; its numbers are from the run
log.

| hypothesis | threshold | run A | run B (final) |
|---|---|---|---|
| H1 deterministic, logged shapes (same + reworded) | ≥ +10 points | +15.0 (61.3 → 76.3) | **+8.75** (65.0 → 73.75) ✗ |
| H1 hybrid, logged shapes | ≥ +5 | +7.5 (68.8 → 76.3) | +6.25 (72.5 → 78.75) ✓ |
| H1 no loss on novel / 72 questions | ≥ −2 | +20 / +4.9 | +20 / +2.1 ✓ |
| H2 compiled coverage of `same` | ≥ 50% | 60% (24/40) | **35%** (14/40) ✗ |
| H2 compiled accuracy vs deterministic on those | ≥ | 87.5% = 87.5% | 100% = 100% ✓ |
| H2 compiled latency | < 20 ms | 3.5 ms p50 | 3.5-5.5 ms p50, 19 ms p90 ✓ |
| H3 optimization cost, no gold | < $0.10 | – | ~$0.087 (advisor $0.043, re-asking the log $0.038, compile $0.006) ✓ |
| H4 indexes change read latency at 5k | < 5% | – | < 0.05% ✓ |

**Decision** (LLP 0003#protocol), for the author:
- **The query log and the advisor:** keep them. The hybrid gain held in both runs. The deterministic threshold was
  missed in one run.
- **Compiled questions:** keep them as a fast path for the shapes they cover (never wrong in run B). Coverage needs
  work (see [Next](#next)).

## Latency and physical design

- **Latency**, live, one question at a time (`deprecated/python/lab/results/workload_latency.json`):
  - the deterministic reader: p50 0.92-0.98 s, p90 1.05-1.25 s
  - compiled templates: p50 5.5 ms, p90 19 ms
  - most of a compiled answer's time is the reader's own filtering in Python (~15 ms at 5k rows); pushing the plan
    into SQL would make it sub-millisecond
- **Physical design** (`deprecated/python/lab/results/workload_physical.json`):
  - The three most-logged plans ran on the evolved database (2,784 expense rows) and on a copy with expenses
    multiplied to 1,002,240 rows.
  - Indexes were chosen by counting the log's filters.

| rows | reader's current path (all rows into code) | filters pushed into SQL | + indexes from the log |
|---|---|---|---|
| 2.8k | 15-17 ms | 0.25-0.49 ms | 0.03-0.14 ms |
| 1.0M | 3.4-5.3 s | 68-121 ms | 1.6-38 ms |

At personal scale, physical design is irrelevant next to a ~1 s model round trip. At a million rows it matters, but
only after the reader pushes filters into SQL.

## What had to be learned

Every item below came from reading the query log or the advisor's report, not from gold answers. Each became a
general rule in code.
1. **The log exposes reader bugs, not just schema gaps.**
   - "How many visits to Field?" went to `events`: Jev saw only a few example values per table. The fix passes the
     stored values a question names (`DetReader._mentions`); on the past log the deterministic reader went from 61.3%
     to 67.5%.
   - A count restricted to rows where Jev's chosen column was filled gave 7 visits to Café Savoy instead of 55.
     Counts now count matching rows.
2. **A new column helps only if the reader stops using the old path.** With the free-text `description` still
   offered, Jev kept filtering on it, and the replay gain was +0.04. A derived column now `supersedes` the free-text
   columns its rules read (`_derived` spec).
3. **The verifier alone can't validate a migration.**
   - One proposal had no "coffee" value, so Jev filed 949 coffees under "drinks". The replay still liked it.
   - The data-side checks catch this class: don't merge values an existing category keeps apart, measured only
     against columns the new one re-categorizes. Otherwise a city "merges" every category.
4. **Catch-all rules hide the right answer.**
   - `(?s).* -> meal` and `category ^dining$ -> other_dining` (inside a dining scope) swallowed the 57-67 dinners
     that merchant association would have placed.
   - Rules that match ≥ 98% of the rows in scope are dropped, and "other…" values count as placeholders.
5. **Columns can apply to part of a table.** A dining-only column is fine; forcing "other" onto non-dining rows
   isn't. Migrations declare a `scope`, and coverage is measured inside it.
6. **Jev confirms spelling variants from the user's own words, not from rows.**
   - Shown the rows, "Onesip" vs "Onesip Coffee" scored 0.62.
   - Shown the messages that produced each spelling, it scored 0.96, and different merchants scored 0.05-0.08.
7. **Some errors are silent.** A confident count on one spelling ("Onesip Coffee": 64 of 91 rows) triggers no signal.
   A code-detected `variants` signal made the advisor see it.
8. **Compiled templates must be general and checked by answers.**
   - Left alone, the model enumerated the literal values it saw ("in June 2024", "Bistro Monk").
   - Plans that differ only by a redundant filter (`unit = 'kg'`) give the same answer, so answers are compared.
   - A capture must never swallow extra words: "Kantýna in July 2024" once mapped to Kantýna, for all time.
9. **The advisor varies.** Over nine advisor runs, the location concept came back as:
   - text rules over messages (rejected: 54-60% coverage)
   - a "duplicate of currency" (rejected by an early, wrong duplicate rule)
   - `place` over 2,664 rows (run A)
   - nothing, in the next run, after a small change to the log
   - `expense_location` over three categories (run B)

   The validator was changing during these runs too. But runs A and B used nearly the same validator and differed
   mainly in the prompt. Every kept location column was 100% right where filled. What varies is whether the concept
   is proposed, and its scope. None of the runs thought of the obvious rule: currency → city.

## Deviations from the protocol

- **Signals were fixed after the first log run:** a stemming bug, generic question words, and the added `variants`
  signal.
- **The reader changed during the round:** value mentions, and count semantics. Both conditions use the changed
  reader. Round 3-4 numbers (LLP 0002) predate it.
- **The advisor's validation grew during the round** (items 2-7 above), designed while looking at this workload's
  log. No gold was used, but the validator may fit this data better than new data.
- **Templates are validated by answers,** not plans only.
- **Spend:** about $1.03 for the whole round, development included: Jev $0.49 measured on OpenRouter, GPT-6 Luna about
  $0.54 estimated from logged tokens. The cap was $2.

## Limitations

- **Small and synthetic.** One simulated life, 80 logged questions and 105 future ones; differences of 1-2 questions
  are noise.
- **The workload's shapes are the simulator's.** Real users repeat themselves less exactly, which matters most for
  compiled templates.
- **Write-time derivation was only smoke-tested.** Four new rows went through the `Engine` hook, and all four got
  the right derived values by code alone:
  - "dinner at Field with Kuba" → dinner, "beers at Vinograf" → drinks (rules)
  - "Bistro Monk 185 CZK" → lunch (merchant association)
  - a Trader Joe's receipt → San Francisco

  No full ingestion ran after the migrations.
- **`forget` doesn't purge `_queries` yet** (LLP 0003#risks).

## Next

1. **Make the advisor stable.**
   - Sample several proposals, or use a stronger model once (the cost is cents), and keep every one that passes.
   - Give it data-derived hints it misses, such as columns that predict the concept perfectly (currency → city).
2. **Templates that map a word to whichever column stores it.** "coffee" is a category, while "lunch" is a
   `dining_occasion`. Then one template covers every kind, which would raise coverage.
3. **Push compiled plans into SQL,** and add indexes by counting the log once tables pass ~100k rows.
4. **Learn routing from the log:** questions whose trusted plans used table X. Unusual phrasings are now the largest
   miss.
5. **Measure write-time derivation on a full stream of new messages,** and purge `_queries` on `forget`.
