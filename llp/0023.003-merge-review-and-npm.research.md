## Verified findings and fixes

### Erasing an empty person

[observed] `packages/core/src/save.ts` reads a revision before awaiting embedding. A first save could read null,
then another instance could erase the person (also leaving null), and the conditional save would succeed after
erasure. Reproduced on Local and actual SQLite; all five adapters had the same reset semantics.

[observed] `packages/core/src/local.ts`, `packages/sql/src/store.ts`, `packages/postgres/src/index.ts`,
`packages/firestore/src/index.ts`, `packages/firestore/src/rest.ts`: every erase now atomically replaces or creates
a random, content-free revision marker while deleting source/derived content, vectors and processing tombstones.
Even an absent person gets a new generation. Prior work cannot match it; repeating erase changes it again.
This is a concurrency marker, not a visible memory record. The host still must revoke future account writes.

Three new Local/SQLite tests failed before the fix. Shared conformance now covers null-before-erase and repeated
erasure, and the real pending-first-save test now returns `ConflictError` with zero restored windows. The same
conformance runs against PostgreSQL and both Firestore adapters.

### Redirect recipients

[observed] The shared provider transport previously followed POST redirects. A compatible gateway could forward
private request content to a second origin outside the declared processors. Two local synthetic servers
reproduced this with 307/308 responses.

[observed] `packages/providers/src/http.ts` forces manual redirects and rejects all 3xx responses without retries
or forwarding. Regression tests assert that the second server receives zero requests and the redirect body's
private text does not appear in the error. Existing configured endpoint/processor policy remains unchanged.

### MCP resource errors

[observed] The dossier resource could expose raw adapter/provider errors even though the equivalent tool
sanitized them. `packages/mcp/src/server.ts` now shares the error boundary between resources and tools, validates
dossier output, and checks cancellation. InMemoryTransport tests cover provider errors, generic adapter errors,
oversized dossiers and a valid empty dossier. The useful response-size guidance remains public.

## Backend migration boundaries

[observed] The initial release review left the backend unchanged. The later integration below targets
`/Users/zvada/conductor/workspaces/therapist-backend/backend-simplify`, which resolves to the linked `ulaanbaatar`
worktree. The product consumes the SDK directly; MCP remains optional. Existing long-input coverage,
saves/corrections and evidence APIs resolve several gaps listed in the older LLP 0023.000 audit.

The review identified three concrete integration gates:

- BetterMind atomically checks `_erasure_jobs/{uid}` inside its Firestore write transactions and initially erases
  `users/{uid}` plus explicitly registered external records. FluidDB's separate `fluiddb_people` tree and revision
  precondition do not participate automatically. Join the host's atomic account barrier and deletion traversal;
  an out-of-transaction lookup or AbortSignal is insufficient.
- BetterMind distinguishes requested pinned saves from proactive unpinned notes. FluidDB `remember` is explicitly
  pinned. Do not blindly map both tool intents onto it.
- BetterMind's selective soft-forget/cutoff differs from FluidDB's source-window deletion, including sibling
  derivations and preserving independent repetitions. Define the product mapping before changing the tool.

[confirmed] (Adam Zvada, 2026-09-28): integrate FluidDB as the primary selected AI memory engine in the linked
workspace, keep the old engine and data, and support Firestore and resumable transfer/background work. This replaces
the initial inferred recommendation for text-only shadow wiring; it does not authorize production deployment.

[observed] The initial backend integration implemented all three gates through a product Store/Records
adapter inside the shared account transaction, truthful imported/proactive origins and pinning, and revision-bound
forget previews plus legacy tombstones/cutoffs. It initially selected legacy until all migration pages completed.
This engine-selection behavior is superseded by the maintainer's subsequent sole-runtime decision in LLP 0023.004:
FluidDB is now the only active engine; bounded import still completes before live memory mutations. Pending work
resumes through a bounded 15-minute cron. The package/release and validation details live in `docs/releasing.md`.
