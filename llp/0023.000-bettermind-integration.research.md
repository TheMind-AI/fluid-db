## Conclusion

[inferred] FluidDB fits BetterMind's TypeScript and Cloudflare architecture. The research supports replacing the
older memory approach; this audit does not establish that FluidDB performs worse. The missing verification is
whether the TypeScript implementation reproduces the measured gains. Preserve product guarantees such as durable
explicit saves, user corrections, privacy and forgetting while retaining FluidDB's researched dossier, per-turn
retrieval and memory-use instructions. Matching BetterMind's internal schema is not itself an acceptance criterion.
The viewer is useful supporting work, not a prerequisite for establishing memory quality.

## How this relates to the benchmarks

[observed] LLP 0019.000 and LLP 0021.000 report recall-on-cue over the same 392 questions from 18 accounts:

| Evaluated configuration | Recall | Input tokens per question |
|---|---|---|
| Product's injected memory baseline | 39.7% | 1,812 |
| Product's stored memory, searched | 44.3% | 1,876 |
| Fluid dossier + linked statements + windows, LLM picker (`conv_best2`) | 73.0% | 9,391 |
| Fluid closed-question picker variant (`conv_best2_jev`) | 71.8% | 9,385 |
| Whole history | 70.0% | 37,387 |

These are substantial measured gains over the evaluated product baseline. They used the Python research pipeline
and its exported product-memory baseline, not a new run of the TypeScript package against the currently inspected
backend. The 55 backend tests establish behaviors, not superior memory quality. LLP 0024.000's TypeScript checks
use deterministic providers and likewise do not measure real-model quality or establish research parity.

[observed] Conversation behavior was measured separately: merely providing `conv_best2` memory led to referring
back after a retelling in 9.5% of tested replies; adding the explicit memory-use directive raised that to 45.8%
(LLP 0021.000). This is a different metric from recall. An adapter must preserve the turn-level retrieval and
prompt-use behavior, rather than assume that an occasional optional search tool reproduces those results.

[observed] The long-input limit below is inherited from the research pipeline:
`deprecated/python/lab/datasets/private_chat.py` also clipped messages at 4,000 characters, and
`deprecated/python/lab/memory/stores.py` clipped statement-extraction input at 12,000. Finding that limit in the port
does not invalidate the benchmark results or demonstrate a new TypeScript regression. It shows an input-coverage
limitation that the reported scores do not rule out.

[inferred] First establish comparable TypeScript quality with the same input, model/picker settings and grader,
then test expanded product scenarios. A dossier can replace five profile blocks if it preserves or improves the
required behavior; separate episode records need not be copied merely because they already exist. Borrow specific
useful guarantees and test cases, not the old memory architecture wholesale.

## Where the systems fit

[observed] BetterMind already separates a generic `@bettermind/memory` package from host storage, providers and
therapy policy. Its API is a Hono Cloudflare Worker; per-user Durable Objects coordinate sessions and checkpoint
leases. FluidDB also has a pure TypeScript core with injected storage and model ports, plus a Hono Worker and
per-person SQLite Durable Object. These boundaries are compatible; their interfaces and data models are different.

| Requirement | BetterMind today | FluidDB today | Integration consequence |
|---|---|---|---|
| Cross-session facts | Active memory records and lexical retrieval | Embedded statements/windows, groups and dossier | Promising semantic retrieval candidate; quality improvement is unmeasured |
| Explicit save | `remember_memory`, requested saves pinned, durable receipt, immediate cache update | Conversation ingestion and model extraction | Needs a structured explicit-write contract |
| Corrections | Actual replacement ID, active/superseded states, pinned-record protection | Retained wordings, repetition/change groups | Preserve user authority and define the active view |
| Dates and identity | People/topics, importance, observed/due dates, actor, language, timezone | Statement kind, text, person/session/window/time/group | Metadata and prompt inputs need extending |
| Opening context | Five profile blocks, upcoming plans/events, recent episode notes | Dossier plus selected statements/windows | A dossier alone does not preserve the product's selection rules |
| Long messages | Whole messages, contiguous windows, atomic cursor, bounded drain | Full raw log, truncated derived/extractor input | Current extraction can miss the end of a processed message |
| Voice sources | Sealed source gate; interrupted assistant playback excluded | Immutable accepted turn IDs | Ingest final eligible messages, not provisional captions |
| Forget | Soft record state plus revision/cutoff preventing relearning | Source-window deletion, vectors, raw turns, tombstones, dossier rebuild | Product semantics must be chosen explicitly |
| Privacy/account erase | Server-owned incognito and erasure barriers | Backend token and processor allowlist; per-person erase | Host remains authoritative; add new storage to erasure orchestration |
| Read latency | Warm in-process retrieval without model calls | Embedding, selection, repetition decisions | Need deadlines, measurement and a prompt-context fallback |
| Inspection | Memory viewer, operation logs, synthetic conversation simulator | Counts/timings, status, typed recall | Reuse UI patterns; add an inspection read model and trace port |

Source map: `BM/packages/memory/src/{model,tools,compose,checkpoint,extraction,recall}.ts`,
`BM/src/domain/memory/{checkpoint,store,tools}.ts`, `BM/src/domain/chat/{privacy,content}.ts`,
`Fluid/packages/core/src/{memory,port,split,extract}.ts`, `Fluid/packages/schema/src/{statement,api}.ts`.

## Contracts to preserve

### Explicit writes and corrections

[observed] `BM/packages/memory/src/tools.ts` distinguishes an explicit user request from a proactive save. An
ordinary fact can be pinned on request; proactive saves have an importance threshold. Corrections validate a real
active replacement ID. A matching existing record can be reused while the contradicted record is superseded.
`BM/src/domain/memory/tools.ts` updates the warm cache on successful writes and forgets. The tool result represents
completed storage, which matters when voice can continue while the operation is pending.

[observed] Fluid's `Memory.Service` exposes ingestion, folding, recall, forgetting and dossier reads. There is no
equivalent explicit-save/pin/actor API. Converting a save into a fabricated chat message would lose these guarantees.

[inferred] Add a typed durable write operation and receipt, with user/extractor authority, replacement validation,
stable IDs and an immediate updated read view. Keep the BetterMind tool surface and product instructions as the
adapter's callers. Do not move therapy policy or `load_skill` into FluidDB's engine.

### Complete input and final voice transcripts

[observed] `BM/packages/memory/src/checkpoint.ts` processes the oldest whole unseen messages within a soft character
budget; a single oversized message remains whole. Additional messages remain unprocessed. The host drains at most
eight checkpoints on session end and one on a turn. Oversized extracted fields receive a rewrite attempt with the
complete source; continued failure leaves the cursor unchanged. See `BM/packages/memory/src/extraction.ts` and
`BM/src/domain/memory/checkpoint.ts`.

[observed] Fluid's `split.ts` takes the first 4,000 characters of each human turn for a window; `extract.ts` takes
the first 12,000 characters of its input. Full text survives in the raw log, but ingestion marks the turn processed.
The dossier also derives from windows. A later retry does not automatically extract the omitted tail.

The deterministic probe used:

```ts
const text = "Earlier context about the class. ".repeat(180) + "cancelled-the-ceramics-class"
```

It ingested that single message through the real `Memory` and SQLite store, with `Testing` providers. A scripted
extractor checked whether its actual prompt included the final marker. Results:

```json
{
  "inputChars": 5968,
  "fullOriginalRetained": true,
  "extractorSawTail": false,
  "derivedWindowContainsTail": false,
  "turnMarkedProcessed": true,
  "providerRequests": 0
}
```

[inferred] Complete-message/chunk coverage and progress tracking are prerequisites for replacement. A fix must
also cover multi-message windows exceeding the extraction budget, preserving assistant context and source IDs.
Keeping a raw log is necessary but does not establish that the memory learned the whole input.

[observed] BetterMind refuses extraction while a source remains open or incomplete, reconciles stale sources,
and checks the checkpoint's cancellation lease. Its storage reader requires sealed source sessions. Assistant
audio marked interrupted is excluded by `BM/src/domain/chat/content.ts`. Fluid's immutable raw IDs make upstream
finalization essential: an early partial caption cannot later be replaced under the same ID.

### Forgetting, privacy and lifecycle

[observed] BetterMind's forget transaction changes selected records to `forgotten`, retaining their text and
reason/time for inspection. It increments a memory revision and advances an input cutoff. Old profiles, episodes
and legacy notes are excluded; future extraction cannot replay earlier transcripts, and stale in-flight
checkpoints cannot commit. Other active facts remain available. Conversation history and an already-open model
context are separate from this operation. See `BM/src/domain/memory/store.ts`.

[observed] Fluid's documented forget operation deletes the selected source windows, their raw turns, sibling
statements and vectors, then rebuilds the dossier. An independent repetition in another window/session remains.
Its tombstones block delayed redelivery of deleted IDs. This is neither BetterMind's selective soft forget nor
account-wide semantic erasure. See LLP 0023#forgetting.

[inferred] Preserve a clearly specified product contract before wiring `forget_memory` to Fluid. A compatibility
layer needs a deliberate policy for unrelated facts in the same window, repeated evidence, pending writes and
future replay. It must not report that every trace was erased when only derived memory changed.

[observed] `BM/src/domain/chat/privacy.ts` makes missing/erroring policy reads incognito, prevents downgrading a
stored incognito chat, and blocks new provider sessions once erasure starts. Fluid's token authenticates the
backend, not a user. A separate Fluid Durable Object is not automatically covered by Firestore erasure.

[inferred] Keep authorization, incognito eligibility, final-source selection and the erasure barrier in BetterMind.
Include Fluid inboxes, rows, vectors, dossiers and any future traces in account deletion coordination. Preserve
each deployment's allowed processors; an existing optional assessor does not imply permission to send every
transcript to another provider.

### Context, policy and latency

[observed] BetterMind's five profile blocks, dated upcoming items and three recent episode notes are assembled
without an LLM. Recall scores words/stems, tags, recency and importance over a bounded loaded set; the host's warm
cache expires after 60 seconds by default. Storage reads up to 300 records before active-state filtering, so the
searchable set can be smaller. See `BM/packages/memory/src/{compose,recall}.ts`,
`BM/src/domain/memory/{tools,store,paths}.ts`.

[observed] Fluid recall embeds the current moment, searches statements and windows, then concurrently selects
from both and detects repetition. With nonempty candidate sets this is one embedding request plus three model
or decider calls; the LLM shim turns decider calls into model calls. Dossier retrieval alone does not need those
calls. Actual deployed latency and cost were not measured. See `Fluid/packages/core/src/{memory,pick,detect}.ts`.

[inferred] Retain cached opening context and existing explicit tool receipts. Preserve Fluid's per-turn memory
retrieval, directive and evaluated retelling behavior, with a deadline, cancellation and a warm-context fallback;
prefetching from stable transcript boundaries is one option. Preserve the voice harness's result byte limits and
operation visibility. Measure the full path rather than infer unacceptable latency from the number of model calls.

[observed] BetterMind keeps product-specific guidance in `src/domain/therapy/memory-guidance.ts` and live per-agent
guidance. Its generic extraction prompt explicitly distinguishes proposed, accepted, attempted, completed and
declined actions; uncertain interpretations stay qualified. It receives language and timezone. Fluid's extraction
prompt currently asks what a therapist would remember and has no equivalent full host-guidance/scope contract.

[inferred] Borrow these evidence and state distinctions. Add host guidance and scope inputs without hardcoding
BetterMind's therapeutic behavior in the reusable engine. Semantic search, repeated-wording groups and retelling
detection are potential additions in the other direction, subject to paired evaluation and false-positive checks.

## Reusing the viewer

[observed] `BM/packages/memory-viewer` is a separate TanStack Start/React application. Its server selects a local
simulation or Firestore reader; server functions validate inputs. Its records and queries still import BetterMind
schemas/codecs and `@bettermind/memory`, so substituting `server/reader.ts` alone will not make it a Fluid viewer.
The inspected app has:

- Overview and current context preview; preview is not a captured historical prompt.
- Searchable/filterable memory table, pins, states, dates, correction links and source IDs.
- Checkpoint/recall/save/forget logs, extractor output versus stored records, and source conversations.
- Episode notes and an optional assessment panel that distinguishes missing/unavailable judgments from zero scores.
- A recall playground using the actual product retrieval implementation without writing an audit event.

Useful reuse points are `components/{memory-table,memory-detail,source-messages,log-entries,context-panel}.tsx`,
the URL-backed filters in `routes/`, the UI primitives, and the validated query boundary in `server/queries.ts`.
`server/data.ts` and `lib/schemas.ts` need replacing or separating from product-specific structures. Current list
reads have fixed caps (for example 1,000 memories and 2,000 overview log entries), not complete cursor pagination.

[inferred] Build a private Fluid viewer application outside the core library, with these views:

| View | Fluid data and behavior |
|---|---|
| Overview | Person/session selection, dossier, inbox/retry state, counts |
| Memories | Statements with original wordings and group repetition/change relationships |
| Evidence | Windows and complete source turns, linked back to the remembered statement |
| Recall | Selected statements/windows and retelling result; candidate scores/decisions when recorded |
| Activity | Ingest, fold, recall, forget and failures; versions, timings, IDs and optional decision traces |

Use authored fixtures or a local SQLite store by default. Keep authentication and storage/provider credentials on
the server, retain private/no-store responses, and keep React/Firestore dependencies out of Fluid's core. Expose
paginated read-only inspection operations for remote use; the present HTTP API provides status/dossier/recall but
does not list raw sessions, windows, statements and groups for a browser. Person discovery belongs to the host's
directory, not enumeration of Durable Objects.

Fluid's existing operational logger stores counts and timings, not a complete historical decision record. An
optional trace port would need retention/deletion rules and persisted snapshots if the viewer is to explain why
an earlier extraction or selection happened. Do not fabricate missing history or present a current recomputation
as the historical decision. A real Fluid recall playground may make provider calls; distinguish explicit live runs
from free fixture/cache inspection.

[observed] Browser inspection used the existing BetterMind viewer with six fictional records for Sam, including a
changed class date, pinned saves and a forgotten record. Table filtering, memory detail, checkpoint source messages
and recall were inspected. Querying "ceramics class" returned the current 15 October memory, not the superseded
8 October record. This demonstrates reusable UI and existing retrieval, not an implemented Fluid viewer.

## Recommended implementation order

All steps here are `[inferred]` proposals, not completed integration work.

1. **Reproduce research quality.** Compare the TypeScript port with the measured Python configuration on equivalent
   inputs and graders, with provider settings frozen and gold labels excluded from prompts. Separate retrieval
   quality from whether the companion actually uses the memory. This needs the capped protocol below; the current
   free fixture is not a substitute. Add complete-input regression cases, distinguishing inherited limits from
   accidental port differences.
2. **Preserve product guarantees.** Implement durable explicit saves/receipts, user correction authority and
   deliberate forget semantics. Add structured dates/scope or other metadata where a product behavior requires it;
   do not require an identical profile/episode schema. Cover pending-save corrections/withdrawals and concurrent
   forgets. Adapt the viewer and authored BetterMind scenarios to inspect these behaviors.
3. **Host adapter and isolated evaluation.** Add `BM/src/domain/memory/fluid.ts` behind the existing checkpoint,
   composition and tool boundaries, including the per-turn memory context path. Preserve auth, transcript
   eligibility and leases. Run old/new stores on the same fictional sessions; keep production memory authoritative
   until the comparison is complete.
4. **Staging decision.** Measure real quality, voice latency, write lag, cost and capacity using a capped, cached
   evaluation protocol. Decide on backfill eligibility and rollback before any production migration.

For storage, first reuse Fluid's per-person SQLite Durable Object, either through its backend-only service or as
a dedicated memory object deployed alongside the application. The public packages can be installed from local
tarballs for a prototype; copying the whole Fluid repository into BetterMind is unnecessary. Keep BetterMind's
Firestore transcript store. A Firestore implementation of Fluid's port is another option, but its transaction and
vector-search contract requires a real adapter and conformance tests; `FirestoreMemoryStore` is not compatible as-is.

Cross-store delivery needs stable person/chat/turn IDs, an idempotent outbox or equivalent retry ownership, and
separate accepted/processed states. Fluid's HTTP inbox acceptance is not a completed extraction receipt. Preserve
that distinction when advancing cursors or confirming a save, and coordinate erasure with pending deliveries.

## Evaluation gates

[inferred] These are the comparison questions, not established improvements:

- Does semantic recall recover older and differently worded/cross-language facts that BetterMind's bounded lexical
  set misses, without surfacing superseded or forgotten facts?
- Do explicit saves, corrections and withdrawals preserve exact durable receipts and state while a voice turn
  continues? Can any old transcript, stale checkpoint, cache or delayed write recreate forgotten memory?
- Are cancelled/declined plans, unknown outcomes and tentative insights represented faithfully in statements,
  dossier/profile and episode context? Can the companion use memory appropriately without falsely saying it remembers?
- Are complete long messages covered, sources sealed, interrupted audio excluded and relative dates resolved in
  the correct timezone/language?
- What are end-to-end p50/p95 recall latency, timeout/fallback rate, write lag and per-session provider spend under
  the existing voice flow? Choose the acceptance budget against that flow's measured baseline.

Start with mechanical tests and the authored cases in `BM/packages/memory-sim/src/evaluation-cases.ts`,
`therapeutic-method-cases.ts` and `voice-scenarios.ts`. The simulator exercises actual composition, tools, storage
and checkpoints, so it is useful inspiration for Fluid's evaluation harness. Model-quality comparisons need a
separate hypotheses-first RFC, allowed processors, response caching and a code-enforced budget under LLP 0001/0024.
Neither the deterministic fixture score nor the historical Python results establishes TypeScript product parity.
