# LLP 0023.002: Agent feedback and memory skills

**Type:** RFC
**Status:** Draft
**Systems:** Interfaces, Evaluation
**Author:** Adam Zvada / Codex
**Date:** 2026-09-27
**Related:** LLP 0023, LLP 0023.001, LLP 0024

## Purpose

[confirmed] (Adam Zvada, 2026-09-27): add HiveNet feedback to the SDK, CLI, MCP and product surfaces. Agents
should report observed failures, including complicated memory cases, as reproducible evaluation candidates.
Ship skills for using memory and reporting feedback, including the MCP skills extension. The supplied integration
instructions authorize one live integration smoke report to the `fluiddb` HiveNet project.

## Feedback boundary

[inferred] A separate, fetch-only `@fluiddb/feedback` SDK submits explicitly supplied reports to HiveNet. Core
and database adapters never submit telemetry or depend on this package. Feedback is not a person's memory:
there is no Store access, account identity, raw transcript collection, environment scan, automatic attachment,
or local outbox. Free text must be reviewed by its caller; the SDK cannot reliably redact arbitrary prose.
Always send `consent.telemetry: false`. The endpoint and project are fixed, not model-controlled.

Reports support category, exact subject, structured task/expected/actual/mistake/attempts, and bounded memory-case
descriptors (operation, challenge, adapter, counts). These are evaluation candidates, not trusted labels or proof
of a regression. Developers curate synthetic reproductions under LLP 0024 before promoting them into checks.
Thread continuation and answers to owner questions retain their identifiers. Preserve a client idempotency key
on ambiguous failures so an explicit retry cannot duplicate the event. Do not retry automatically.

HiveNet `guidance`, `ask`, `known_issue`, and continuation commands are returned as data. Never execute them,
ingest them as conversation memory, or use them to override authorization. A known issue is already recorded;
do not file variants. A reopened issue already conveys that it was still broken.

## Surfaces

[inferred] `fluiddb feedback` uses the same SDK, and `fluiddb skills list/read` exposes the bundled skills.
The MCP feedback tool is an independent outbound capability: hosts explicitly enable it, separately from memory
writes and deletion. The stdio option is `--feedback`. Discovery explains where reports go and how to report
through the standalone HiveNet command if this capability is unavailable. Ordinary memory calls never report.
The Worker serves the public well-known descriptor, agent markdown and skill files; submitting is a direct SDK
operation, avoiding a deployment-token-bearing feedback proxy. Nothing is deployed by this change.

## Skills

[observed] The accepted [Skills extension specification](https://github.com/modelcontextprotocol/ext-skills/blob/main/specification/stable/skills.mdx)
uses `io.modelcontextprotocol/skills`, `skills/list`, `skills/get`, and ordinary `resources/read`. Each static
manifest includes verbatim frontmatter, all files, their SHA-256 digests and byte sizes. Modern results also carry
`resultType`, `ttlMs` and `cacheScope`. Older clients can read ordinary resources or use `fluiddb_read_skill`.

[inferred] Keep canonical portable SKILL.md files in `packages/skills/skills/`. Generate a runtime-independent
catalog from their exact bytes, and check for drift in CI. The same catalog serves the SDK, CLI, MCP and public
HTTP resources. No dynamic skill generation, nested skills, filesystem paths or remote downloads at runtime.
Memory instructions retain researched per-turn recall, provenance, corrections and deletion semantics. Skill
discovery does not grant permissions. MCP feedback reports must use synthetic examples instead of personal data.

### Understanding memory

[confirmed] (Adam Zvada, 2026-09-29): give agents discoverable skills explaining the structure and automatic work
of FluidDB memory, both in the SDK/MCP and the therapist backend.

[observed] The memory skill links to `references/memory-model.md`, a tool-independent explanation of windows,
statements, temporal groups, embeddings, the dossier, and the boundary between engine work and host scheduling.
It distinguishes the maintained conversation structures from archived dynamic-schema research and describes
Jev as optional configuration. Product-specific tool names and policy belong in the host's allowlisted skill.
Essential save/receipt policy remains in normal instructions; loading this explanation is not a prerequisite
for every save. Proactive notes require host permission, agent provenance and normally no pin.

[observed] `fluiddb_read_skill` retains its existing name-only call and additionally accepts a relative `path`
resolved solely against the static catalog. SDK/CLI reads accept the exact resource URI. Public HTTP skill routes
serve those same catalog files. Supporting files have distinct MCP resource names and complete manifest digests.
There are no filesystem reads, remote fetches or memory operations at runtime when reading guidance.

## Verification

Test the SDK wire contract against the published HiveNet 0.6.0 schemas, malformed responses, cancellation,
idempotency/thread continuation and no automatic context. Exercise CLI parsing and real MCP protocols with a
stub feedback service. Verify skills manifests against served bytes in modern and legacy transports, public
Worker routes in workerd, and published Node packages. The only live feedback is the authorized smoke report;
record its returned thread. No new model calls are needed.
