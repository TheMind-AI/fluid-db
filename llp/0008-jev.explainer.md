## Summary

Jev (TypeSafe's "System One" model, `typesafe/jev-1.13` on OpenRouter's `/systemone` endpoint) doesn't generate text.
- **What it answers:** it is given a JSON `state` and typed questions, and returns calibrated probabilities.
- **Question types:** Choice (pick one of named options), Noul (a yes/no probability), Score (a level on a scale).
- **Cost:** $0.042 per 1M input tokens; output is free. About 0.3 s per request.

In FluidDB, Jev makes every closed decision, so an LLM is needed only to write, compile and fall back.
[confirmed] (Adam Zvada, 2026-09-24): the user asked to use Jev "inside designing the database … even the planning,
like querying, creating the database" (dictated). Client: `deprecated/python/lab/common/jev.py`, cached like every model call.

## What it is used for

| decision | where | why Jev |
|---|---|---|
| does this message need a write? | write gate (LLP 0005#the-jev-gate) | recall 100%, 0.28 s, $0.02 per 1k (§4) |
| did the user write this, or is it a document? | source guard (LLP 0005#source-guard) | blocked 4 of 4 injections (§10) |
| which value of a column fits this message? | compiled writer choice columns; derived columns | closed set, calibrated |
| same entity? same merchant? | dedupe, canonicalization (LLP 0007) | 0.84-0.96 for true spelling variants given the user's messages, 0.05-0.08 for different merchants |
| does the newer row replace the older? | supersession | 4 of 4 real replacements (§22) |
| table, operation, period, filters | deterministic reader (LLP 0006#routing) | every option exists in the database |
| does this result answer the question? | verifier (LLP 0006#verifier) | decides when to fall back to an LLM |
| is this answer correct? | judge (LLP 0009#graders) | 96.7% agreement with Opus, $0.006 for 300 (§20) |

## Where it works

- **Row-level, closed decisions.** Its probabilities are calibrated here: answerability AUROC 0.994 (§4). A low
  confidence on an ambiguous name (0.74 vs 0.95) is a reason to ask the user (§4, §19).
- **Speed.** About 0.3 s per request, and requests run in parallel.
- **Routing a question to memory stores** (LLP 0013.000): one yes/no per store in one request. Same accuracy as GPT-6
  Luna, 0.28 s vs 3.1 s.
- **Tagging every message for consolidation:** five yes/no aspects per message, 16 messages per request. It ranks
  them as well as Luna does (AUROC 0.997-1.0 vs 0.990-1.0) at 1/6 of the cost and 1/33 of the latency.
- **Verifying a computed answer:** AUROC 0.952 vs Luna's 0.932.

## Where it does not

- **Schema-level judgments** ("should these tables merge?"). It ranks usefully, but its absolute scores don't
  separate the cases (§12).
- **Merges judged from rows alone.** It is under-confident: 0.56-0.76 for true variants. Give it the user's messages
  (LLP 0003.000).
- **Anything that requires producing a value.** It only chooses among options.
- **Comparing details:** "does this row record the message's values?" AUROC 0.68 vs Luna's 0.81 (LLP 0013.000).
- **Absolute probabilities can be conservative.** At p ≥ 0.5 it finds 69% of the messages that set a reminder or
  schedule something, though it ranks them near perfectly. Calendar invites get 0.2-0.6.

## Patterns

- **Closed sets only.** Every option is something the database contains, or "none", so Jev can't invent data.
- **Thresholds live in code.** For example: merge at ≥ 0.8, ask at 0.5-0.8, fall back below 0.7.
- **Batch small questions.** Several rows per request, each with its own question, keep requests few (8 rows per
  request for derived columns).
- **Speculate.** Ask the likely next questions in parallel with the first (the stage-2 slots for the top BM25 tables).
- **Show the evidence Jev needs.** The plan in words for the verifier; the user's messages for merges; the message
  that recorded the newer row for supersession.
- **One yes/no per aspect, not one choice among aspects.** A single choice per message loses its second aspect (a
  preference inside a birthday message); independent yes/no questions keep both (LLP 0013.000).
- **Cascade: Jev as a cheap high-recall gate, an LLM after it.** Choose the gate's threshold for recall from data
  (0.15 keeps 97% of intentions and passes 3% of messages), then let the LLM extract from what passes.
- **Word options as tests, with counterexamples.** "A report of what the user did tonight does not count" moved
  "climbing tonight" out of intentions.

## Cost and latency

- **Typical spend:** a deterministic read is ~6 Jev requests, ~10k tokens, ~$0.0004-0.0005. A write gate is ~$0.00004.
- **Round 5 spent $0.49 on Jev in total,** including development runs (LLP 0003.000).
- **Round 7:** the five-aspect pass over 5,050 messages cost $0.065; the round spent $0.29 on Jev in total, including
  routing, grading and development.
- **Reliability:** occasional 5xx responses are retried; a torn cache file counts as a miss (§10).
