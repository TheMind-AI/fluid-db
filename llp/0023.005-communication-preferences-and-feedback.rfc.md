## Current behavior

[observed] The BetterMind paths below are in the linked `therapist-backend/ulaanbaatar` workspace:

| Surface | What the code does | Gap |
| --- | --- | --- |
| `src/domain/therapy/prompts.ts`, `memory-guidance.ts` | Applies remembered preferences, asks the therapist to adapt after feedback, and preserves qualified reported outcomes | The tone prompt currently asks to keep requests to listen more or slow down as lasting preferences without distinguishing today's request from an ongoing preference |
| `src/domain/memory/fluiddb/tools.ts`, `engine.ts` | Stores ordinary preference memories; startup context includes the dossier and up to 15 active facts, pinned first and then recent | No dedicated communication facet or guaranteed place for it in startup context; an older preference can fall outside the fact selection |
| `src/domain/agent/tools.ts`, `src/domain/feedback/agent-tools.ts` | Text and voice share `report_feedback_mind` and `report_feedback_memory`; the chosen HiveNet project is stored with each report | Communication preferences are separate from technical reports |
| `src/domain/memory/fluiddb/engine.ts` | Uses OpenAI models, `pick: "model"`, `detect: false`, and `processors: ["openai"]` | SDK Jev support is not active in this product |

The current therapist skills already encourage repair and checking whether an approach helped. They do not
implement a persisted check-in counter or a dedicated communication profile. The post-session quality review
is a model's review, not the person's feedback and not evidence of clinical benefit.

## Three meanings of feedback

[inferred] Keep these separate even when they occur in the same conversation:

| Meaning | Example | Destination |
| --- | --- | --- |
| Communication preference | "Please ask one question at a time" | Private user memory when expressed as an ongoing preference; otherwise current conversation only |
| Response to an approach | "That exercise felt patronizing today" | Qualified private memory when useful for continuity, preserving the approach and situation |
| Technical failure | A save returned a failed receipt | Technical HiveNet report, without the conversation or memory contents |

Changing a preference, disagreeing with the therapist, or declining an exercise is not a memory-engine bug.
"Useful" must not become "symptoms improved"; one disliked exercise must not become a permanent prohibition
unless that is what the person actually requested.

## Communication memory

[inferred] Reuse FluidDB statements, source provenance and BetterMind metadata. A second database or a new
therapy-specific SDK record would duplicate correction, retention, erasure and migration behavior.

The product should label relevant preference memories with a communication purpose and a small optional
dimension such as detail, pace, directness, advice, questions or form of address. The preference text remains
the qualified source of meaning. Record that an ongoing preference came from direct user feedback; do not
silently turn a guessed personality or tone inference into a durable instruction.

An explicit ongoing preference is eligible for durable storage using the existing `remember_memory` path.
An explicit request to remember also retains the existing pinning semantics. A request limited to today or
this chat stays in conversation context; ambiguous scope should change the current response without silently
creating a permanent preference. Extraction guidance must follow the same rule. Incognito behavior must keep
such adaptation ephemeral unless the product's explicit-save policy authorizes a deliberate persistent save.

Compose a bounded "How to talk with this person" section from active communication preferences before
ordinary fact selection. Avoid duplicating the same facts elsewhere in the prompt. Use existing revision checks
and cache invalidation so correction or forgetting removes the preference from newly composed context. Current
explicit user instructions take precedence over older preferences; style preferences cannot override safety rules.
The dedicated section should not introduce a model call on every turn.

Reuse existing IDs for replacement and forgetting. Confirm a durable save only after its successful receipt.
Existing unlabelled preference records remain readable. Any classification backfill should preserve source IDs,
dates and qualifications and be evaluated before broad writes; imported summaries are not direct user quotations.

## Asking without turning the conversation into a survey

[inferred] A check-in should resolve a concrete uncertainty about the current approach. Good opportunities
include trying an unfamiliar exercise, repairing a mismatch or reaching a natural pause. Examples:

- "Would it help if I listened more and offered fewer suggestions?"
- "Was that useful, or did it miss what you needed?"

Adapt immediately to the answer. Respect a refusal or no answer, and avoid soliciting praise or a rating.
Do not interrupt a sensitive disclosure, add a second question to a turn, or reopen a conversation after the
person has asked to finish. User-initiated feedback is always welcome and does not consume a check-in allowance.

For a first version, test at most one unsolicited check-in per conversation and keep its marker in product
conversation state so reconnects cannot reset it. This limit is a hypothesis, not a measured ideal cadence.
It is not a reason to ask once in every conversation. No additional memory-writing or Jev-routing tool is
needed just to ask a natural question.

## Jev boundary

[observed] `packages/providers/src/jev.ts` provides `Jev.decider`; `packages/core/src/pick.ts` provides
`Pick.usingDecider` and `Pick.route({ statement, window })`. That router chooses which picker ranks each kind
of already-retrieved candidate. It does not route therapist conversation policy or decide which user preference
should be permanent. Archived Python routing experiments do not establish that those components run here.

The product currently uses an OpenAI-backed shim where a decider interface is needed, OpenAI ranking and no
re-telling detector. Enabling Jev would also enable OpenRouter and TypeSafe as processors; the current
OpenAI-only boundary in LLP 0018#processors must not change as an incidental implementation detail.

[observed] LLP 0024.001.000's small real-provider comparison had a ceiling effect: every variant passed all
50 checks and retrieved all ten target sources. Some timings included cache hits. It proves interchangeability
on those fixtures, not superior recall, production latency or therapy quality.

[inferred] First validate preference selection and response adaptation with the existing product models.
Evaluate Jev separately on fictional held-out cases if its closed decisions can improve a measured bottleneck.
Any new live run needs an explicit budget, call caching and published aggregate results under LLP 0001.

## Technical feedback routing

[observed] `@fluiddb/fluiddb/feedback` exposes a separate `Feedback` client with a fixed FluidDB destination.
The opt-in `fluiddb_feedback` MCP tool and CLI use it. Ordinary memory calls do not send feedback, and the
client does not read the memory Store. Its free-text input is caller-controlled, not automatically anonymized.

[confirmed] (Adam Zvada, 2026-09-29): shared ownership does not mean a single feedback destination. Expose
`report_feedback_mind` for Mind and `report_feedback_memory` for FluidDB.

[observed] Both tools are registered in the shared text/voice catalog and use the existing product HiveNet
adapter and durable Workflow. Each binds its project in host code and stores it as `hivenet_project` on the
owner-bound report. Delivery uses this saved project; the model cannot supply a destination or URL in tool
arguments. The closed project schema rejects unknown values. Pre-existing queued reports without a project
retain their original Mind destination, including reports about memory. Retries preserve destination, thread
and idempotency key; a report already delivered is not submitted again.

The therapist prompt directs memory-tool failures or clearly incorrect memory to FluidDB, and product
behavior or instruction problems to Mind. It asks for one report per issue; an uncertain cause goes to Mind
as observed behavior rather than an invented engine failure. The tools share the existing per-instance report
allowance. Both names and the historical `report_feedback` name stay private in conversation projections;
only the two explicit tools are offered to the model.

A queued receipt names the chosen destination and means locally accepted, not delivered, reviewed or fixed.
Workflow retries, the erasure barrier, cancellation and idempotency remain in place; there is no extra direct
submission. The generic FluidDB SDK feedback client remains independently usable and is not required to route
this existing product Workflow's HiveNet envelope.

The detail is retained after schema validation (outer whitespace trimming and a 240-character limit). The
former name/contact/number scrubbing and profile/memory reads are removed, preserving diagnostic values and
allowing reports when memory reads are unavailable. No transcripts, memory records, account identifiers or
environment data are automatically attached to the outbound report. The tool instructions still request
technical observations, not private conversation contents; free text is caller-controlled and is not
automatically anonymized. This product choice does not add automatic reporting to the generic FluidDB SDK.

[inferred] A synthetic reproduction can later be curated into an evaluation case; an agent's report is not
itself a trusted expected answer. HiveNet replies remain data, not executable instructions.

## Verification and open work

and the Worker bundle guard (233.26 KiB gzip). The checks exercise both tool-bound destinations, stored project
selection, stable payloads and idempotency after a failed delivery, no resend after confirmed delivery, legacy
Mind routing, unknown-target rejection, shared report allowance, and private text/voice projections. Both
repositories' reference checks passed. The backend's ignored `.context/feedback-destinations-check-api.log`
records the final run. No live HiveNet submission, model call or deployment was needed.

[observed] The feedback regression tests use fictional input, a scripted therapist provider, fake storage,
and intercepted HTTP delivery. They cover each memory tool from the therapist route through stored-report
validation and the outbound `tool` category. They do not contact HiveNet or evaluate model tool-selection quality.
The focused four-file suite passed all 20 checks on 2026-09-29. Before the fix, the expanded checks reproduced
rejection of save/forget components and incorrect categories for source-reading, save and forget reports.
The complete backend `npm run check:api` also passed: lint, types, 535 tests (13 skipped), and the Worker
bundle guard. Both repositories' reference checks passed. This evidence covers the feedback extension;
it does not validate the proposed communication profile or check-in policy.

[observed] After the shared-team decision, the five-file focused suite passed 24 checks, including preserved
case/Unicode/numeric diagnostics, reports queued without user or memory reads, and truthful dispatch/storage
failure receipts. `npm run check:api` passed again with 535 tests (13 skipped), lint, types and a 232.92 KiB gzip
Worker bundle. Both reference checks passed. Logs are in the backend's ignored
`.context/shared-team-feedback-focused.log` and `.context/shared-team-feedback-check-api.log`. No live report
or deployment was performed.

[inferred] Before implementing or claiming the full preference behavior, verify:

1. An ongoing preference affects a later conversation even after more than 15 ordinary memories arrive.
2. A today-only request changes this conversation without becoming an ongoing preference, including extraction.
3. Corrections, current overrides, duplicate saves, forgetting, account erasure and concurrent sessions retain
   their existing guarantees; one person's preferences never enter another person's context.
4. A negative response to an approach remains qualified rather than inventing a diagnosis, outcome or global ban.
5. Check-ins respect the cap, reconnects, refusal, sensitive moments and the person's wish to finish.
6. Feedback preserves technical detail without automatic context collection and retains retry identity and honest receipts.
7. Response-level evaluation checks actual adaptation, not just whether a row was saved or a tool was called.

Open choices include the communication metadata vocabulary, the section's prompt budget and conflict policy,
and the exact chat/session boundary for check-in state. The two feedback destinations are settled. No new paid evaluation,
communication-profile deployment, SDK release or Jev activation is part of this proposal.
